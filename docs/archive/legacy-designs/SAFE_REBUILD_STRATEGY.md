# SAFE REBUILD STRATEGY

## 1) Architecture Audit Summary

### Current Data Flow (Observed)
1. Raw ingest is primarily imported into operational tables, especially supplier transactions (idempotent inserts).
2. Posting is generated through business events and posting rules when running through canonical APIs.
3. Historical repair scripts also generated entries directly (phase-style and reclassification style), which increased derived data volume.
4. Traceability exists in two forms:
- Native business_events based posting.
- Backfilled source_documents and source_document_links for legacy entries.

### Main Structural Problem
1. Operational truth and derived accounting artifacts are mixed in the same UX views.
2. Rebuild/repair scripts created technical entries that are valid accounting artifacts but noisy for daily operations unless explicitly separated by type.
3. Category coding (example: 31001) was heuristic in backfill and must be promoted to canonical dictionary mapping.

## 2) Data Lineage Map

### Canonical Lineage (Target)
1. Source Ingest Layer
- Raw files and imports (JSON, import SQL, staging_movements).
2. Operational Layer (Authoritative Business Facts)
- suppliers
- supplier_transactions
- cash_transactions
- inventory_movements
- work_orders and equipment tables
3. Mapping Layer (Canonical Dictionaries)
- item canonical map
- equipment canonical map
- expense and posting category map
- posting groups and control accounts
4. Posting Event Layer
- business_events
- posting_rule_resolutions
5. Ledger Layer (Derived)
- journal_entries
- journal_entry_lines
- account_balances and snapshots
6. Traceability Bridge Layer (Derived)
- source_documents
- source_document_links

### Hard Rule
Any derived layer must be fully reproducible from operational layer plus canonical mapping layer.

## 3) What Can Be Safely Deleted

Delete only derived/regenerated artifacts, not source operations.

1. Generated journal entries created by replay/backfill scripts (phase or reclass local_id patterns).
2. Regenerated bridge artifacts:
- source_documents
- source_document_links
- posting_rule_resolutions
for the rebuilt scope only.
3. Recomputable aggregates and snapshots:
- account_balances
- period inventory snapshots
- reconciliation caches
4. Derived linkage rows proven to be algorithmic backfills:
- transaction header links generated by post-facto matching where source key is missing.
5. Frontend cached datasets:
- client caches and persisted query state.

## 4) What MUST Be Preserved

1. Raw source artifacts:
- raw JSON import files.
- import scripts and idempotent import SQL.
2. Original operational records:
- supplier_transactions
- cash_transactions
- inventory_movements (original rows and original timestamps)
- work_order and equipment usage source rows
3. Master entity identifiers:
- suppliers.code
- items.code
- equipment type identifiers
- warehouses names/codes
- cost center ids/codes
4. Manual business inputs done by users in production.
5. Original document references and external document numbers.

## 5) Required Rebuild Plan

## Step 1 — Cleanup
1. Freeze write operations for affected modules.
2. Export full database backup and checksum it.
3. Delete only derived artifacts in scoped order:
- source_document_links
- source_documents
- posting_rule_resolutions
- journal_entry_lines (scoped to generated entries)
- journal_entries (scoped to generated entries)
- recomputable balances and snapshots
4. Keep operational source tables untouched.
5. Produce before and after row-count report per table.

## Step 2 — Canonical Mapping Layer
1. Build canonical dictionaries with strict keys:
- item canonical dictionary (name variants to item_code)
- equipment canonical dictionary (aliases to equipment_type_id)
- description canonical dictionary (normalized tokens)
- posting category dictionary (including 31001 semantics)
2. Enforce one mapping source of truth table per domain.
3. Reject ambiguous matches (no fallback to nearest text).
4. Add explicit unresolved queue table for unmatched rows.
5. Add mapping version column and effective date for reproducibility.

## Step 3 — Rebuild Inventory
1. Reconstruct inventory movements from source imports/staging in deterministic order.
2. Preserve original movement ids where possible; otherwise maintain immutable source_key.
3. Recompute balances from movement sequence only.
4. Re-link transaction headers only with deterministic key rules.
5. Log unresolved relations into missing_relationships report.

## Step 4 — Rebuild Equipment Registry
1. Rebuild equipment master from canonical equipment mapping.
2. Rebind operational usage to equipment_type_id and usage_mode.
3. Separate owned versus rental by explicit fields, not by name heuristics.
4. Validate each equipment-linked transaction has required center and season references.
5. Output integrity report for orphan equipment references.

## Step 5 — Rebuild Posting Engine
1. Recreate business_events deterministically from operational source rows.
2. Regenerate journal entries only via posting engine path.
3. Generate journal lines with rule_slot and source_ledger metadata.
4. Rebuild source_documents and source_document_links from event and entry ids.
5. Recompute balances and reconciliation artifacts.
6. Validate trial balance and module totals after rebuild.

## Step 6 — Frontend Reintegration
1. Rewire API bindings to canonical fields only.
2. Rebuild dropdown data sources from canonical dictionaries.
3. Re-enable filters with strict parameter contracts.
4. Normalize labels from canonical dictionary layer.
5. Remove hidden fallback display logic that masks null relations.
6. Add explicit UI warnings for unresolved relationships.

## 6) Integrity Rules (Mandatory)

1. No fallback logic that silently guesses account or entity.
2. No synthetic data to fill missing relationships.
3. Every missing relationship must be logged with reason and source row id.
4. Every regenerated record must include regeneration batch id and mapping version.
5. Rebuild must be idempotent and replayable.

## 7) Risks and Integrity Concerns

1. Mixed legacy and rebuilt journals can duplicate financial impact if scope boundaries are unclear.
2. Heuristic category codes can misroute AP subaccounts if not canonically defined.
3. Inventory link backfills can create false associations in duplicate signature groups.
4. Traceability bridge may look complete while source semantics are still unresolved.
5. Frontend filter mismatch can hide valid data and create false incident perception.

## 9) Backend and Frontend Synchronization Plan

1. Backend contract first:
- Lock response schemas for suppliers, treasury, inventory, and gl entries.
2. Frontend adapter pass:
- Map incoming payloads through typed adapters.
3. Filter contract tests:
- For each page filter, verify query parameter to SQL predicate mapping.
4. Traceability UX contract:
- Source tab must show source event and source document when present.
- If absent, show explicit unresolved reason from API.
5. Release gates:
- Data integrity gate.
- API contract gate.
- UI rendering and filter gate.

## 10) Execution Governance

1. Dry run in remote clone environment.
2. Produce signed comparison report:
- before and after counts
- financial totals parity
- unresolved relationships list
3. Approve go live only if all critical gates pass.
4. Keep rollback package ready:
- full export
- rebuild batch metadata
- replay scripts.
